# Nix DevShell Action

Load a Nix devShell environment into your GitHub Actions steps.

Languages: [日本語](README-ja.md)

## Prerequisites

- Nix must be installed with Flakes enabled.
- `openssl` must be available. GitHub-hosted runners include it by default.

## Basic Usage

This action runs `nix print-dev-env` against the given flake to generate a bash script that sets up the devShell environment. It then extracts the variables that the script adds or changes, filters them for safety, and writes them to `$GITHUB_ENV` and `$GITHUB_PATH`. Later steps can then use the devShell environment as if they were running inside it.

Previously, you had to prefix every step with `nix develop -c`:

```yaml
- uses: cachix/install-nix-action@v31
- run: nix develop -c -- pytest
- run: nix develop -c -- ruff check .
```

Run this action once up front, and later steps can just use plain commands with the same tools and environment variables as inside the devShell:

```yaml
- uses: cachix/install-nix-action@v31
- uses: tacbooon/nix-devshell-action@v1
- run: pytest
- run: ruff check .
```

## Inputs

### flake

Path, URI, or flake reference (installable). Defaults to the current directory (`.`).

```yaml
- uses: tacbooon/nix-devshell-action@v1
  with:
    flake: ./subdir
```

```yaml
- uses: tacbooon/nix-devshell-action@v1
  with:
    flake: github:owner/repo
```

```yaml
- uses: tacbooon/nix-devshell-action@v1
  with:
    flake: .#ci
```

### export-path

Glob patterns used to filter which paths are written to `GITHUB_PATH`. Use a newline-separated list for multiple patterns.

This action does not export every path the devShell adds to `PATH`. Only paths matching at least one `export-path` pattern are written to `GITHUB_PATH`. By default, only paths matching `/nix/store/*` and `$GITHUB_WORKSPACE/*` are exported.

The following example adds `/path/to/bin/*` while keeping the default patterns. Note that setting this input overrides the defaults, so they must be listed explicitly if you still need them:

```yaml
- uses: tacbooon/nix-devshell-action@v1
  with:
    export-path: |
      /nix/store/*
      /path/to/bin/*
      $GITHUB_WORKSPACE/*
```

Suppose the devShell adds `/path/to/bin/dir` and `/path/to/other/dir` to `PATH`. `/path/to/bin/dir` matches `/path/to/bin/*`, so it is written to `GITHUB_PATH` and available in later steps. `/path/to/other/dir` matches nothing, so it is skipped.

Only `GITHUB_WORKSPACE` and `PWD` can be expanded as environment variables in this option.

### export-env

Glob patterns used to filter which environment variables are written to `GITHUB_ENV`. Use a newline-separated list for multiple patterns.

By default, nothing is written to `GITHUB_ENV`. To export variables, add patterns matching their names. The example below exports only variables matching `APP_*` and `DB_*`:

```yaml
- uses: tacbooon/nix-devshell-action@v1
  with:
    export-env: |
      APP_*
      DB_*
```

Suppose the devShell defines `APP_NAME` and `MYAPP_URL`. `APP_NAME` matches `APP_*`, so it is written to `GITHUB_ENV` and available in later steps. `MYAPP_URL` matches nothing, so it is skipped.

The following are never written to `GITHUB_ENV`, even when they match a pattern: `_`, `ACTIONS_*`, `BASHOPTS`, `CI`, `EUID`, `GITHUB_*`, `IFS`, `OLDPWD`, `PATH`, `PPID`, `PWD`, `RUNNER_*`, `SHELLOPTS`, `SHLVL`, `UID`.

## Design

By default this action does not export every path and variable, in order to avoid unexpected side effects in later steps. A devShell rewrites far more variables than the ones you define explicitly, and neither your own steps nor other GitHub Actions are designed to inherit all of them implicitly.

Internally, the action uses `nix print-dev-env` instead of running `nix develop`. This avoids the implicit `bash-interactive` download/build that `nix develop` performs, and keeps execution fast with no per-step shell startup overhead.

## Security

This action sources the script generated by `nix print-dev-env`, which includes your devShell's `shellHook`. That means arbitrary code from the given flake runs inside the workflow. Only point `flake` at sources you trust; an untrusted flake can execute arbitrary code with the workflow's permissions.
